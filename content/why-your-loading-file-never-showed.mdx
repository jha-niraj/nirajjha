We built a skeleton for the orders page. Right shape, right rounded corners, the shimmer and everything. It went in `app/orders/[id]/loading.tsx`, which is exactly where the docs say to put it.

Nobody ever saw it. Not in development, not in production, not on a throttled connection.

The file was correct. The reason it never rendered had nothing to do with the file, and there turned out to be four separate ways to cause it.

## What the file actually is

`loading.tsx` is not a loading screen. It is one thing, and everything below follows from knowing it:

> Next wraps your [segment](term:segment) in a `<Suspense>` and uses this file as the fallback.

That is the entire feature. It is [sugar for a Suspense boundary](https://nextjs.org/docs/app/api-reference/file-conventions/loading) you would otherwise write yourself.

So the question "why does my skeleton not show" is really "why is this boundary never triggered", and a boundary triggers on exactly one condition: something inside it [suspends](term:suspend).

The ordinary version: a waiter takes your order to the kitchen. The fallback is the bread they leave on the table. If the kitchen has your dish ready before the waiter has turned around, no bread appears. Nothing is broken. There was simply no wait to fill.

## Reason one: nothing in the segment waits

Ours was this. The page component did not await anything.

The data was fetched in a client component underneath, in a `useEffect`, into `useState`. That is a perfectly ordinary React data fetch, and it is invisible to Suspense. The server had nothing to wait for, so it rendered the page immediately and the boundary never fired.

```tsx
// Never suspends. React has no idea this is pending.
useEffect(() => {
  fetch(`/api/orders/${id}`).then(setOrder);
}, [id]);
```

The fix is to move the fetch into the server component and `await` it. Then the segment genuinely suspends, and the skeleton has a reason to exist.

This is worth internalising beyond skeletons. An [effect](https://react.dev/reference/react/useEffect) that sets state is opaque to React's scheduling: it runs after paint, so the first render always shows the empty state. React's own guidance is [that most data fetching does not belong in an effect](https://react.dev/learn/you-might-not-need-an-effect), and the dead skeleton is one of the clearer symptoms.

## Reason two: the route is static

If a route has no dynamic inputs, Next renders it at build time. There is no per-request work, so there is nothing to wait for on a visit.

This is the one that catches people in development, because a [static route](term:static-route) still feels like it is loading the first time. It is not. It is downloading.

The tell is in the build output that [`next build`](https://nextjs.org/docs/app/api-reference/cli/next) prints: `○` means static, `ƒ` means dynamic on demand. If the route you wrote a skeleton for is marked static, the skeleton is dead code.

Reading that table is a habit worth forming. It is the same output that tells you a stray `cookies()` call has quietly dropped a route out of static generation, which is the opposite failure and a much more expensive one.

## Reason three: the await is above the boundary

This one is quiet and it is the one worth remembering, because the code looks right.

A `loading.tsx` wraps its own segment. It does not wrap the layout above it. If the slow `await` lives in `app/orders/layout.tsx`, the layout is suspending **outside** the boundary that your skeleton provides, so the fallback that fires is the parent's, or none at all.

```tsx
// app/orders/layout.tsx
export default async function Layout({ children }) {
  const org = await getOrg();          // blocks here
  return <Shell org={org}>{children}</Shell>;
}
```

The user stares at the previous page while that resolves. Your skeleton is one level down, patiently waiting for a render that has not started.

Move per-request work down into the page, or wrap the slow part in its own `<Suspense>` inside the layout.

## Reason four: it is fast enough not to bother

React does not show a fallback for a boundary that resolves almost immediately. A skeleton that flashes for 30ms is worse than no skeleton, so it is deliberately avoided.

If your local database answers in two milliseconds, you may never see the file work locally, and then see it constantly in production where the same query crosses a region. Throttling the network does not help, because the wait is on the server. Add an artificial delay to the server component if you need to prove the file works.

## Where loading.tsx stops being the right tool

It is per segment, and that is its real limit.

`loading.tsx` blanks the **whole** segment. If your page has a header, a summary and one slow table, the file replaces all three with skeleton, including the parts that were ready instantly. That is worse than useless: you are hiding fast content behind slow content.

The moment more than one thing on a page has a different speed, you want boundaries inside the page instead:

```tsx
export default function Page() {
  return (
    <>
      <OrderHeader />                       {/* instant, never hidden */}
      <Suspense fallback={<TableSkeleton />}>
        <OrderLines />                      {/* slow, streams in */}
      </Suspense>
    </>
  );
}
```

Now the shell paints at once and only the slow region shows a placeholder, which is what [streaming](https://react.dev/reference/react/Suspense) was for in the first place.

The other boundary is the one from the prefetch story: this file makes navigation *feel* instant. It does nothing to the time the data takes. If the table takes two seconds, the skeleton is on screen for two seconds. The fix for that is on the server, not in the fallback.

## The short version

- `loading.tsx` is a `<Suspense>` around the segment. It fires when something inside [suspends](https://react.dev/reference/react/Suspense), and never otherwise.
- Fetching in `useEffect` does not suspend. Move the await into the server component.
- Static routes have nothing to wait for. Check for `○` against `ƒ` in the build output.
- An await in the layout suspends above your boundary, so the skeleton never gets its turn.
- Very fast resolutions skip the fallback on purpose, so local speed can hide a real production wait.
- One slow region on an otherwise fast page wants a `<Suspense>` in the page, not a whole-segment skeleton.
